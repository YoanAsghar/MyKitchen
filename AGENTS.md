# AGENTS.md

MyKitchen: `backend/` (.NET API) + `frontend/` (Next.js). Local-only app, no CI.

## Specs (spec-driven development)
- **`docs/specs/` is the functional source of truth.** One spec per feature (`docs/specs/<slug>.md`) with context, scope, user stories + acceptance criteria (Dado/Cuando/Entonces), API contract, data model, realtime events, edge cases and test mapping. Index/template: `docs/specs/README.md`, `docs/specs/_template.md`.
- **Spec-first:** before coding a new feature/behavior change, write/update its spec; the acceptance criteria become backend tests. After implementing, update the spec's status and this file if architecture changed.
- Existing specs (SPEC-001..015): auth, multi-tenancy, realtime, navigation-layout, restaurant-onboarding, staff-management, tables, order-composition, order-payment, order-history, kitchen-display, catalog, expenses, marketing-site, admin-panel.
- When the spec and code disagree, fix one of them in the same task — never leave them out of sync.

## Run the app
- Backend: `cd backend && dotnet ef database update && dotnet run` (PostgreSQL, listens on `http://localhost:3000`). Run from `backend/` (appsettings.json is resolved there).
- Frontend: `cd frontend && npm install && npm run dev` → `http://localhost:5173` (port is hardcoded via `next dev -p 5173 --webpack`).

## Gotchas
- The READMEs (`README.md`, `frontend/README.md`) are **stale**: they describe Vite + React. The real frontend is **Next.js 16 App Router** (`src/app/`), React 19, Tailwind v4 (`@tailwindcss/postcss` via `postcss.config.mjs`). Trust the code, not the docs.
- Frontend API base is `NEXT_PUBLIC_API_ROUTE`; services call `${apiRoute}/api/v1/<Resource>`. **`src/config.tsx` now derives `apiRoute` at runtime from `window.location.hostname:3000`** (override via `NEXT_PUBLIC_API_ROUTE`). This keeps the backend same-site with whatever host the browser uses (localhost or LAN IP) so auth cookies flow — never hardcode a specific IP in `.env.local`.
- Backend CORS allows the origins in `appsettings.json` -> `Cors:AllowedOrigins` (local + LAN frontends) with `AllowCredentials`. Auth is cookie-based (`AuthorizationCookies`); frontend fetches must pass `credentials: "include"` (see `src/services/UserServices.tsx`).**Cookies are `SameSite=Lax`, so the page and API must be same-site (same hostname; any port) or the cookie is never sent** — the runtime `apiRoute` derivation above is what keeps them aligned.
- Every controller is `[Authorize]`; role policies `AdminOnly`/`ManagerOnly` gate destructive/management actions, and a base `RestaurantScopedController` resolves the tenant from the cookie claim (`restaurantId`, never a client-sent id).
- Entities are PascalCase on the wire (e.g. `PaymentMethod`, `tableId`); `ProductController`/`OrderController` etc. focus backend logic. DB connection string is committed in `backend/appsettings.json`.
- Real-time sync is wired end-to-end: backend `RestaurantHub` (`Hubs/Hub.cs`, `MapHub<RestaurantHub>("/hub")`, `[Authorize]`) broadcasts `OrderUpdated`/`OrderClosed`/`TableCreated`/`TableDeleted`; event names are centralized in `HubEvents` (backend) and mirrored in `frontend/src/services/SignalRService.ts` — keep them in sync. The **global order + table state lives in `frontend/src/app/OrdersContext.tsx`** (provider wraps the app inside `GlobalProvider`); Mesas + Cocina + Ordenes consume it, so never reintroduce per-page order/table state. `syncOpenOrder`/`clearOpenOrder` are now **commit points** (no debounce): they persist immediately and are only invoked by the Mesas composition panel's "Crear orden"/"Actualizar orden" button, never per keystroke.
- **Frontend order composition is local-first** (`frontend/src/app/kitchen/[id]/mesas/tableInformation.tsx`): adding/removing products, guests and tip only touch the component's local draft state — nothing is sent to the backend while composing. There are **no tabs anymore** (`currentTab` was removed): the panel is split side by side — **left** = product search + a category accordion (grouped by `Category`, fed by the `categories` prop), **right** = the order-detail table + propina. A **full-width Total bar** spans both columns and holds the single commit button (**"Crear orden"** when the selected table has no OPEN order, **"Actualizar orden"** when it does; purple), which commits the draft via `syncOpenOrder` (or `clearOpenOrder` when the draft is empty). Below that, the **payment block** (`TablePayment.tsx`) only renders when the selected table already has a created OPEN order (`table.order` present): "Métodos de pago" (Efectivo/Transferencia/Tarjeta) + **"Procesar pago"** (`POST /api/v1/Order`). There is no separate "Editar orden" button — editing is just composing again and pressing the commit button. The Mesas grid is `flex-1` and the panel is capped (`lg:w-[45%] xl:w-[42%] max-w-[760px]`) with small, panel-tuned sizing; the draft re-seed effect (`appliedKeyRef`) still mirrors remote hub changes onto the panel (last-write-wins).
- Orders now have a `Status` (`OPEN` = in-progress, drives Mesas + Cocina; `PAID` = history, drives Ordenes). `GET /api/v1/Order` returns only `PAID`; `GET /api/v1/Order/active` returns all `OPEN`; `PUT /api/v1/Order/table/{tableId}` upserts a table's open order (empty cart clears it) and broadcasts via the hub; `POST /api/v1/Order` is the payment flow (marks `PAID`, clears the table's open order, broadcasts `OrderClosed`). `TableController.GetTables` attaches each table's open order.
- SignalR's JSON protocol is configured separately from MVC (`AddSignalR().AddJsonProtocol(...)` includes `JsonStringEnumConverter`) so hub payloads serialize enums as strings like the REST API.
- Backend is `.NET 10` (`net10.0`), EF Core 10. Schema changes require EF migrations (`dotnet ef migrations add ...` + `dotnet ef database update`).

## Routing
- **Public:** the marketing site under `frontend/src/app/home/` route group (`/home` landing, `/home/pricing`, `/home/contact`, `/home/registro`) and the auth section under `frontend/src/app/auth/` (`/auth/login`; `/auth/*` for future auth pages). `RootClientLayout` treats `/home*` and `/auth*` as **public paths**: no auth redirect, no app `Navbar`, and they render as normal scrollable pages (no `h-screen` app chrome).
- **App (business):** every business page lives under `frontend/src/app/kitchen/[id]/` where `[id]` is the restaurant id: `/kitchen/{id}/mesas`, `/kitchen/{id}/cocina`, `/kitchen/{id}/carta`, `/kitchen/{id}/ordenes`, `/kitchen/{id}/admin`. Pages render inside the app chrome (`Navbar` + `h-screen` layout). Tab navigation goes through `RootClientLayout.handleTabChange`, which reads the current `{id}` from `useParams` and pushes `/kitchen/${id}/${tab}`.
- **Administration is a fully standalone section at `/admin/{id}`** (own `layout.tsx` with its own sidebar/topbar, logout and "Ir a mi restaurante"; no app `Navbar`, no kitchen chrome). `RootClientLayout` treats `/admin*` as authenticated-but-standalone (no auth redirect skip, no app chrome) and bounces `/admin/<otherId>` back to `/admin/{sessionRestaurantId}`. The app `Navbar`'s Admin tab and the marketing **"Gestionar mi restaurante"** both point to `/admin/{restaurantId}`. The sidebar (sub-routes under `/admin/{id}/`) currently has: **Panel** (`/`), **Empleados** (`/empleados`, full CRUD + roles via `UserServices`), **Productos** (`/productos`, full CRUD via `ProductServices`; the category field is a `<select>` populated from the `Category` table), **Categorías** (`/categorias`, full CRUD via `CategoryServices`), and placeholders for Mesas, Historial/Ventas, Gastos, Reportes/Métricas and Configuración (all `ComingSoon` pages under a shared `admin/components/ComingSoon.tsx`). Sidebar active state derives from `usePathname`; on mobile the topbar has a `<select>` navigator. Only `admin`/`owner` can manage (`User`/`Category` mutations and `Product` are manager-gated server-side; `Category` reads are open to any authenticated user since the carta needs them).
- **Root `/`** now always redirects to `/home` (the landing), for everyone: no more auto-redirect into the restaurant for logged-in users. When a session exists, `MarketingNavbar` (top-right) replaces the login/register CTAs with **"Ir a mi restaurante"** (→ `/kitchen/{restaurantId}/mesas`) and, for `admin`/`owner` only, **"Gestionar mi restaurante"** (→ `/admin/{restaurantId}`); it holds a placeholder while `isAuthChecking` to avoid flashing the logged-out CTAs. `RootClientLayout` treats `/` as a public path.
- Shared marketing primitives (`PrimaryBtn`, `GhostBtn`, `FieldInput`) + route helper `marketingPath()` + `MarketingPage` type live in `src/app/home/components/ui.tsx`. `MarketingNavbar`/`MarketingFooter`/`AppMockup` are in `src/app/home/components/`. Each view (`LandingView`, `PricingView`, `ContactView`, `RegistroView`) is mounted by a `page.tsx` under `src/app/home/` and does its own `useRouter` navigation.
- **Marketing style direction (current):** mirrors the app's mesas aesthetic — neutral near-black `#0a0a0f` page bg, cards `bg-white/[0.02]` + `border-white/[0.06]`, text via white opacity tiers (`text-white/35` body, `text-white/20`-`/30` labels, `text-white` headings), single green accent `#22c55e` for CTAs/toggles/status. No purple, no glow orbs, no gradient text, no Bebas watermarks. The old Figma visual language (dark `#030014`, purple `#22007c`, gradient `#D6C7FF→#AB8BFF`, glow orbs) is **retired** for marketing pages; `FigmaDesigns/` + `docs/landing-site-figma-brief.md` remain as layout/structure reference only.
- `/home/registro` is **wired**: it calls `POST /api/v1/Restaurant/register`, which creates a `Restaurants` row + its **Owner** `User` (username = email, same password; the restaurant row itself stores no credentials) and returns a session. `/auth/login` keeps its real auth (`handleLoginButton` in `src/app/auth/login/Login.tsx`).
